# H200 branch: Qwen3.8-27B long-prompt TTFT on one NVIDIA H200 (SM90)

This branch (`h200`) re-targets the project at a single **H200 SXM (Hopper, CC 9.0)**. The goal is unchanged:
minimum time to first token (TTFT) for one long request (64K / 128K / 256K input tokens) on one GPU, with the
same prompts, serving flags and evaluation scripts as the SM120 work in [results.md](results.md). The SM120
kernels and numbers on `main` are kept as the reference design; nothing here is validated on SM120.

## Results so far (2026-11-01)

Reference matrix, one H200 (GPU 4), four configurations back to back under identical conditions
([validation/h200-matrix-gpu4-20261101.md](validation/h200-matrix-gpu4-20261101.md)); single request, prefill
chunk 8192, mean of two measured runs after one warm-up; the first generated token is identical to stock BF16 in
every configuration and run. Sparse = FA4 block-sparse attention with this repo's block selection, tau 0.95,
64-row selection, FA4 patches 1-3 (static tile order). FP8 = vLLM's CUTLASS SM90 FP8 W8A8 GEMM.

| input | stock vLLM (BF16, FA3) | sparse attention | dense + FP8 GEMM | sparse + FP8 GEMM |
|---|---:|---:|---:|---:|
| 64K | 6666 ms | 6323 ms (-5.1%) | 5043 ms (-24.4%) | **4657 ms (-30.1%)** |
| 128K | 16040 ms | 13789 ms (-14.0%) | 12679 ms (-21.0%) | **10426 ms (-35.0%)** |
| 256K | 42259 ms | 35557 ms (-15.9%) | 35550 ms (-15.9%) | **28789 ms (-31.9%)** |

The sorted tile dispatch (patch 4, now the default) adds another -2.2% at 256K (35.7 -> 34.9 s in a separate
A/B). Speed operating point, tau 0.9 + sorted dispatch + FP8 GEMM (GPU 4, same stock reference): **4529 / 9652 /
25197 ms = -32% / -40% / -40%**, at the tau-0.9 quality (ΔNLL +0.002 / +0.011 / +0.027, top-1 0.996 / 0.977 / 0.957). Output quality of the sparse path (teacher-forced vs the BF16 dense output, needle retrieval) is in the
status log below: ΔNLL +0.0007 / +0.0071 / +0.0105 nat at 64K / 128K / 256K, top-1 agreement 0.992 / 0.977 /
0.973, needle retrieved everywhere. For comparison the SM120 release reports 6677 / 15203 / 36156 ms for its
best configuration on an RTX PRO 6000; the H200 stock baseline alone is 6666 / 16040 / 42259 ms.

## What changes on Hopper

Facts that drove the SM120 design, and their H200 counterparts (spec-sheet values marked *spec*; measure before
relying on them):

| | RTX PRO 6000 Blackwell (SM120) | H200 SXM (SM90) | consequence |
|---|---|---|---|
| SMs | 188 | 132 | wave quantisation targets change (24 heads x m_blocks should be a multiple of 132) |
| memory | 96 GB GDDR7, ~1.8 TB/s | 141 GB HBM3e, 4.8 TB/s *spec* | KV gather + quantise + transpose in the hook is ~2.7x cheaper; two 256K contexts fit |
| shared memory / SM | 128 KB (99 KB usable per CTA in the DSL) | 228 KB (227 KB per CTA) | 128-row FP8/BF16 tiles with multi-stage TMA pipelines fit without register-resident tricks |
| tensor cores | `mma.sync` only (HMMA ~455 TFLOPS measured) | `wgmma` (async, warpgroup) + TMA + clusters/DSMEM; BF16 ~989 / FP8 ~1979 TFLOPS *spec* | the SM120 `mma.sync` kernels are not competitive here; an SM90 kernel must be FA3-style (wgmma, warp-specialised producer/consumer, TMA) |
| DSMEM | 3-6 GB/s (unusable) | fast | cross-CTA cooperation (split-KV reductions, cluster multicast of K/V) is on the table |
| stock vLLM prefill attention | FlashAttention-2 (paged), 305 TFLOPS | FlashAttention-3 (`vllm_flash_attn` FA3, head_dim 256) | the dense baseline is far stronger; the attention share of TTFT must be re-measured before assuming sparsity pays |
| GEMM | cuBLAS BF16 ~392 TFLOPS of ~414 | CUTLASS/cuBLAS BF16 and FP8 W8A8 (`--quantization fp8`) | FP8 GEMM is again "free" from vLLM; needs the dense+FP8 row that `main` never measured |

Model facts that are architecture-independent: 64 layers, 16 full-attention (every 4th) with GQA 24/4 and
head_dim 256, 48 GatedDeltaNet linear-attention layers (chunked prefill kernels, Triton), MLP 5120 -> 17408,
vocab 248K, max context 262144. For a single long request the 48 linear-attention layers and the MLPs are
O(N); only the 16 attention layers are O(N^2). Where the time goes at 64K vs 256K on H200 is the first thing
to measure.

## Plan

1. **Baseline and breakdown.** Stock vLLM TTFT at 64K / 128K / 256K (`bench_stock.sh`), then a per-layer-type
   time breakdown of one prefill chunk at each length (attention / GDN / MLP / norm+misc) with
   `torch.profiler` or `nsys`. Decide from the breakdown whether attention, GEMM or the linear-attention path
   is the lever at each length.
2. **Cheap wins first.** `--quantization fp8` (vLLM SM90 FP8 GEMM) with dense attention, prefill chunk size
   aligned to 132 SMs for the FA3 grid, `--max-num-seqs 1`, CUDA-graph/eager settings. These establish the
   "dense + FP8 GEMM" row missing from `main`.
3. **Block-sparse prefill on SM90.** Keep `sm120_attn/sparse_prefill.py` (block means, tau selection, per-request
   caches, vLLM hook: all architecture-neutral) and replace the kernel: an FA3-style CuTe DSL kernel (wgmma,
   TMA, producer warp + two consumer warpgroups, per-(head, 128-row block) BSR block lists) for BF16 first,
   FP8 (e4m3) second. The retired FlashInfer BSR path in `sparse_prefill.py` is a quick functional reference.
4. **Quality gates** as on `main`: teacher-forced ΔNLL / top-1 agreement against the BF16 dense output and
   needle retrieval at all three lengths (`scripts/validate_generation.py`, `scripts/teacher_forced_eval.py`).
5. Record every measurement under `docs/validation/` with the GPU, clocks, chunk size and git revision.

Order of work: #1 (done) -> #2/#3 (copies, ~6% of 64K) -> #5 (attention-side fusion, needs FA4 edits) -> #6
(GEMM epilogues, needs the CuTe DSL SM90 GEMM; also the entry point for FP8 in stage 4).

**Stage-2 conclusion after the compiled-mode profiles (2026-11-01).** The table above was derived from an
*eager* profile. With torch.compile on (the serving configuration) Inductor already fuses the norm / gating /
copy chains (#1, #2, #3, #7 shrink to 2-3% of the prefill together; the hand-fused RMSNorm gave 0 to -4%), and
cuBLAS BF16 GEMM runs at the H200's sustained rate (680-805 TFLOPS isolated, 549 ms per chunk, matching the
profile), so #6 cannot gain on BF16 either. What remained worth doing on the BF16 side was inside the attention
kernel (#4b, #5): the paged block-sparse loads and the mask-function and scheduling fixes to FA4 (patches 1-4),
which brought the sparse kernel from 86% to 91% tensor-pipe activity and removed the tail on skewed lists. The
BF16 fusion budget left is < 5% of TTFT; the next real levers are FP8 (stage 4: GEMM done through vLLM,
attention needs a new hdim-256 FP8 kernel) and lower tau where quality allows.

## Stage 3 input: how skewed is the sparse work per CTA on real prompts?

`SM120_SPARSE_LIST_STATS=1` (FA4 path, tau 0.95, 64-row selection; `scripts/validate_generation.py` on GPU 4,
3 prompts x all layers/chunks): per call, ratio of the longest (head, q-block) list to the mean list, and the
coefficient of variation of the per-head mean list length.

| input | calls | max / mean list length | per-head CV |
|---|---:|---:|---:|
| 64K | 144 | 1.64 | 0.15 |
| 128K | 400 | 1.86 | 0.24 |
| 256K | 912 | 1.71 | 0.23 |

The longest CTA carries 1.6-1.9x the average work and heads differ by ~20%; FA4's static order (reverse m
block, then head) ignores both. With ~11.6 waves of 1536 CTAs per layer-chunk the tail cost is bounded by
roughly (max/mean - 1) / waves ~ 5-7%, consistent with the 4% imbalance NCU showed on *uniform* random lists.
That is the budget for a list-length-sorted persistent schedule (stage 3, first step) and for splitting the
longest lists across two cooperating SMs with a DSMEM combine (stage 3, second step).

## Two-GPU serving: prefill/decode split (direction proposed 2026-11-01)

Setting: GPUs 4 and 5, several concurrent requests, long prompts. Proposal: disaggregate prefill (P) and
decode (D); keep the stage-1 sparse + FP8 stack on the P GPU; put the Meld-style cross-SM work and aggressive
fusion where their preconditions hold, i.e. decode.

Why decode is where stages 2 and 3 pay: a decode step at 256K context reads 64 KB x 256K = 16 GB of attention
KV per request (3.4 ms at 4.8 TB/s; 8 concurrent requests -> 27 ms per token), plus 54 GB of BF16 weights
(27 GB with FP8) per step regardless of batch, plus ~150 MB of GDN state per request. It is memory- and
latency-bound with strongly variable per-request work: exactly the split-KV + combine structure, dynamic
imbalance and intermediate traffic the paper targets, and the 640 launches per token that a persistent
megakernel removes. Planned order on the D GPU: (1) block-sparse *decode* attention reusing the prefill block
means and tau selection (halves KV reads), + FP8 KV cache; (2) split-KV decode kernel with DSMEM just-in-time
combine across a cluster (the Meld mechanism); (3) persistent decode megakernel if bubbles remain.

Feasibility facts checked so far:
- Interconnect: all eight H200s are NVLink NV18 (18 x 26.6 GB/s ~ 478 GB/s per direction via NVSwitch); GPUs 4
  and 5 share NUMA node 1. A 256K request's 16 GB KV + GDN state moves in ~40 ms.
- vLLM 0.30.0's NIXL connector carries SSM/conv (hybrid) state (`kv_connector/v1/ssm_conv_transfer_utils.py`,
  hybrid handling in `nixl/pull_worker.py`); constraints and the NIXL runtime install are being checked.
- NIXL runtime: `nixl[cu12]==1.5.2` (UCX backend initialises; plugins UCX, GDS, POSIX, ...). The hybrid-model
  transfer requires the DS conv-state layout: both engines must run with `VLLM_SSM_CONV_STATE_LAYOUT=DS`
  (otherwise the connector asserts "3-read Mamba conv transfer requires DS conv state layout"); prefix caching
  off on both sides, same `--block-size` on P and D. With a KV connector the engine allocates the KV cache in a
  strided (cross-layer) layout, so the paged FA4 path's contiguous view fails; the hook now checks contiguity
  and falls back to the gathered path. Launcher: `scripts/h200/pd_serve.sh` (tmux session `pd`),
  client: `scripts/h200/pd_client.py`, sweep: `scripts/h200/pd_bench.sh`.
- Structural alternative to compare on the same hardware: TP=2 (halves TTFT directly, 2 all-reduces per layer
  over NVLink) and two independent replicas. PD does not shorten a single prefill; it removes the mutual
  interference between chunked prefill and decode (TPOT spikes of 60-80 ms per 8192-token chunk today).

## Notes for stage 4: FP8 on SM90

Facts checked in the installed stacks (flash-attn-4 4.0.0b37, vLLM 0.30.0):

- FA4 CuTe FP8 attention is **SM100-only** (`interface.py`: "FP8 is only supported on SM100 for FA4 CuTe"); the
  SM90 CuTe forward has no FP8 path (no descale handling, no in-smem V transpose). FP8 wgmma on Hopper needs
  both operands K-major in shared memory, so V must be transposed on chip (FA3's C++ does it with
  ldmatrix/stmatrix); that is the "special FP8 instruction" work if we want FP8 *sparse* attention here.
- vLLM's FA3 (C++) supports FP8 e4m3 Q/K/V with descales on SM90 and the FP8 KV cache ("FP8 KV cache requires
  FA3 on SM90"), but has no block-sparse lists. Options for stage 4 attention: (a) add FP8 operands to the FA4
  SM90 CuTe path (CuTe DSL, our kernel), (b) add block lists to FA3 C++ (rebuild vLLM's vendored extension),
  (c) keep BF16 sparse attention and take FP8 only in GEMM. (c) is measured already (dense + FP8 GEMM
  -25/-21/-15%; sparse + FP8 GEMM pending), (a) is the natural continuation of our kernel work.
- FP8 W8A8 GEMM is vLLM's CUTLASS SM90 kernel (`CutlassFP8ScaledMMLinearKernel`, per-tensor online scales); the
  stage-2 GEMM-epilogue fusions (SwiGLU) would be built on the same CUTLASS/CuTe SM90 GEMM.
- **Measured (2026-11-01, `scripts/h200/bench_fa3_fp8.py`, GPU 5,
  `validation/h200-fa3-fp8-vs-bf16.log`): vLLM's FA3 FP8 forward is 2x *slower* than its BF16 forward at
  head_dim 256** (8K x 64K: 31.9 vs 17.2 ms; 8K x 256K: 143.6 vs 72.6 ms, 362-387 TFLOPS), with 5.3e-2 relative
  error from per-tensor e4m3 scales. The vendored FA3 FP8 path is evidently not tuned for hdim 256 on Hopper
  (FA3's FP8 numbers are for hdim 64/128), so FP8 attention on this model is not a drop-in: a stage-4 FP8 sparse
  kernel must be written for hdim 256 (K-major FP8 wgmma operands, V transposed on chip, P in registers, FP8 K/V
  blocks read from an FP8 KV cache) and would have to beat 720 TFLOPS BF16 by enough to matter (attention is
  36% of the sparse 256K prefill, so a 1.4x kernel is ~10% TTFT). FP8 GEMM, by contrast, is already captured.

## Notes for stage 3: cross-SM fusion (Meld, SOSP'26)

"Taming Dynamism on GPUs: Cross-SM Kernel Fusion via SM Cooperation and Just-in-Time Reduction" (He et al.,
SJTU; code: github.com/he-jingkai/tilelang.dataflow, built on TileLang/TVM). What transfers to this project:

- **Problem match.** Block-sparse prefill is exactly the "dynamic cross-SM dependency" case: the work per
  (head, 128-row q block) CTA varies with the selected block count (tens to thousands of KV blocks), so a
  static grid has a long tail, and splitting long rows into sub-tasks needs a combine (rescale + accumulate
  O/LSE) that today would be a second kernel and an HBM round trip.
- **Mechanisms.** (1) Persistent *wrapper* CTAs draining per-SM instruction queues of handlers (iter = partial
  attention over a block sub-list, reduce = merge partial O/LSE) instead of a hardware grid; (2) just-in-time
  reduction: the producer SM pushes its partial (O tile fp32 + row max/sum) into the consumer SM's shared
  memory over the cluster interconnect (DSMEM: `mapa` + `st.async`/TMA + mbarrier `arrive.expect_tx`), so the
  consumer reduces in SRAM without waiting; (3) hybrid primitives: intra-cluster via DSMEM, cross-cluster via
  HBM buffers + flags, because clusters are confined to a GPC; (4) heterogeneous cluster dispatch: H100 GPCs
  are 2x18, 5x16, 1x8, 4x2 SMs, so a single cluster size wastes SMs; Meld launches concurrent kernels with
  cluster sizes 16/8/2 on separate streams (an H200 has the same 132-SM layout; verify with the topology
  probe before relying on it); (5) `setmaxnreg` redistribution between producer/consumer warpgroups and
  compute-first shared-memory allocation with the remainder as communication slots; (6) instruction
  prefetch so the load for sub-task i+1 overlaps compute of sub-task i.
- **Plan for us.** After stage 2 (fused FA4-style pipeline), turn the sparse attention CTA into a handler,
  add a split-list handler + DSMEM combine for the longest rows (balance), and fuse the per-layer chain
  selection -> attention -> O-projection as stages in one persistent kernel. Reported gains in the paper for
  GQA attention on H100 were 1.02-1.32x over the best baseline, more under imbalance.
